# 平台边界合同

本文回答一个问题：什么属于设备平台，什么属于业务应用。它是仓库内最高级别的产品合同，不是功能清单、实施路线图或当前实现说明。

## 产品定位

设备平台是内部维护的 IoT 设备接入与控制平台。当前第一个真实使用方是共享单车应用，第一个真实设备类型是智能锁。共享单车应用是平台使用方，不是平台业务域；智能锁是当前设备样本，不限制平台长期边界。

平台由唯一超级管理员治理，并允许多个普通 User 在被分配的 Project 范围内执行技术管理。它不是多租户 SaaS、组织员工协作系统或共享单车运营后台。

## 管理与访问模型

### 人类管理

- 登录主体统一为 `User`。首次安装创建唯一超级管理员；后续普通 User 只能由超级管理员创建，不开放自行注册、邀请注册或公开注册。
- 超级管理员治理全部 User、Project、Device 与平台级能力，其全局权限不依赖 Project 管理关系；平台不提供第二个超级管理员、超级管理员停用或身份变更入口。
- 每个 Project 必须且只能指定一个有效 `manager_user_id`。普通 User 可以管理多个 Project，但只能访问和管理分配给自己的 Project 及其技术资源。
- 当前不建设 Project 多成员、多负责人、组织、部门、岗位或复杂人类 RBAC；普通 User 之间没有菜单、按钮或角色差异。
- Web 管理后台是技术管理和诊断控制台。后续移动端可以作为 Project 范围移动技术运维端，但不因此成为共享单车运营工作台、客户门户或应用业务端。

### 机器访问

- 业务应用通过 Project 范围的机器身份访问平台；机器身份与人类 User 身份彼此独立。
- Device Gateway 和厂商云 Provider 使用各自技术凭据接入。
- 凭据保护、请求校验和 Project 数据隔离属于平台责任；这些能力不等同于人类 RBAC。

## Project 与 Device

`Project` 是一个业务应用的机器接入、数据隔离和平台人类授权范围，不是租户、组织或客户账户。当前共享单车应用是一个 `Project`。`manager_user_id` 只决定普通 User 对该 Project 技术资源的管理范围，不改变业务应用的机器身份、业务用户或行业权限。

Project 可以保存机器凭据、允许来源地址和事件回调端点等技术配置。共享单车应用内部的客户、景区、区域或团队不会因此成为设备平台 Project；只有真实出现独立凭据、设备归属、回调或数据隔离需求时，才重新评估是否需要新的 Project。

- Project 只能由超级管理员创建，并在创建时指定一个有效管理 User；超级管理员可以把 Project 转交给另一个有效 User。
- 普通 User 可以维护其 Project 的基本信息和技术设备，但 API Key、IP whitelist、Webhook endpoint/secret、凭据轮换、dead delivery 重发、模拟器与全局诊断仍只属于超级管理员。
- 停用普通 User 前必须先转交其管理的全部 Project，任何已提交状态都不得出现无管理 User 的 Project。

- 每个 `Device` 必须且只能通过 `project_id` 属于一个 `Project`。
- 不设计一个 Device 被多个 Project 共享、多对多归属、跨 Project 可见或协作所有权。
- Device 跨 Project 转移不是当前需求，不提前为它增加模型复杂度。
- 在应用实体关系上，平台只保存 `Project -> Device`。
- 自行车、车队、景区、用户、订单、行程、计费等关系由共享单车应用保存；业务应用保存自己到平台 `device_id` 的引用。

## 平台负责

平台负责设备及其技术通信事实：

- Project 接入配置和机器身份。
- User 身份认证、唯一超级管理员治理和 Project 范围人类授权。
- Device 身份、类型、型号、技术标识、能力、生命周期和连接状态。
- 统一 Gateway/Provider 边界下的设备接入。
- 命令接收、校验、幂等、投递策略、派发尝试、回执、最终结果、超时和允许的取消。
- 设备上报状态、必要的遥测和用于接入诊断的原始协议或 Provider 消息。
- 规范化技术事件及其向业务应用的可靠投递。
- Webhook 签名、重试、失败记录和受控重发。
- 平台技术操作的审计与诊断。
- 在真实项目明确需要时提供通用位置、轨迹和电子围栏能力，并报告进入或离开围栏的技术事件。

某项能力属于平台边界，不代表它已经实现或进入当前完成定义。是否实施由当前真实目标和已确认需求决定。

## 四层命令责任

设备命令按以下四层分工，不能把某种设备的能力提升为 Platform Core 的全局业务语义：

| 层                       | 责任                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Platform Core            | 通用 Command envelope 和生命周期：Project/Device 归属、capability/action identifier、payload、状态、幂等、投递、Attempt、ACK/Result、timeout、cancel 和 Event。 |
| Device Type Capability   | 某类设备的具体能力语义与最小 profile，包括 payload 校验、在线要求、重放/补偿安全性、风险等级、timeout 和默认投递策略。                                          |
| Gateway/Provider Adapter | 将 capability action 映射为设备协议或厂商请求，并把厂商接受、设备 ACK 和最终执行结果映射回通用结果语义。                                                        |
| Business Application     | 决定为什么执行动作、谁有权触发，以及技术结果如何改变订单、计费或其他业务状态。                                                                                  |

Core 不枚举具体 Device Type 或 Provider 的 action。具体 action、payload 与安全属性进入 Device Type Capability 合同，厂商映射进入 Provider 合同。Core 不得出现设备类型专用表、API 路径、方法或按具体 action identifier 分支的设备语义。当前只需要最小充分的 capability profile，不建设动态低代码规则引擎或假设中的万能能力模型。

## 业务应用负责

共享单车及其他业务应用负责设备事实之上的行业与运营含义：

- 自行车、车队、骑行人、客户、景区和运营人员；
- 订单、行程、预约、计费、退款和结算；
- 可租、使用中、待调度或维修中等业务状态；
- 用户是否有权发起设备动作，以及动作结果对订单的含义；
- 运营区、禁停区、还车点等围栏的业务分类；
- 围栏事件触发的还车、订单、收费、通知或运营动作；
- 业务报表、业务审计和业务角色权限。

平台普通 User 是技术资源管理主体，不等同于共享单车用户、景区运营人员或其他业务应用角色。业务应用仍决定业务上的谁可以触发动作；平台只验证当前人类 User 或 Project 机器身份是否可以进入技术命令链路。

平台可以报告设备进入或离开某个围栏，但不判断能否还车、是否结束订单或是否收费。

## 接入边界

### 南向接入

设备直连、厂商云和模拟器服从同一 Gateway/Provider 抽象：

```text
Device Platform Core
  -> Direct-device Gateway
  -> Vendor-cloud Provider
  -> Simulator Provider
```

传输协议、厂商认证、字段转换和厂商错误映射留在适配器内；平台核心统一 Device、Command envelope、Attempt、Result、State 和 Event 语义，device type profile 定义具体 capability。只实现当前具有真实协议、设备、厂商合同或验收证据的接入，不为假设中的协议提前抽象。

### 北向接入

业务应用使用 Project 机器身份查询设备、提交命令和读取技术结果，并通过可靠 Webhook 接收规范化事件。Web 与后续移动技术运维端使用人类 User 身份进入相同 Project 范围的技术资源。两类身份不得互换；北向接口不实现业务订单、业务用户、计费或运营流程。

## 设备模型规则

共享模型只保存稳定的设备概念。锁、仪表、传感器及后续设备差异进入最小 device type/capability profile、类型化 payload、适配器映射和受控扩展字段。

不向通用 Device 模型加入自行车专属字段，也不为尚未接入的设备类型预先建设万能字段集。

## 明确非目标与未决事项

以下内容不属于平台目标：

- SaaS 租户管理；
- 组织、部门、员工、岗位、Project 多成员或多负责人；
- 通用人类 RBAC、菜单权限或按钮权限；
- 自行车与设备等应用资产归属关系；
- 用户、订单、行程、计费、支付、结算和行业运营；
- 通用工作流、低代码、CRM、ERP 或业务通知系统；
- 一个 Device 的多 Project 归属；
- 没有真实接入依据的设备类型或协议抽象。

OTA、固件管理、批量操作、规则引擎、告警、长期遥测保留策略和新增事件投递机制均为未决事项。它们不是当前承诺，只有真实需求与验收条件明确后才能进入目标合同。

## 决策检验

新增能力前依次回答：

1. 它是否描述 Device、技术连接、技术命令、上报状态、规范化事件或通用设备位置行为？
2. 它是否由当前真实项目需要，或为现有已确认链路的可信运行所必需？
3. 它能否不依赖共享单车或其他应用的业务名词与业务流程？

第 1 或第 3 项为否时，能力属于业务应用。第 2 项为否时，即使概念上属于平台，也不进入当前目标。

## 演进规则

不从想象中的未来项目推导通用性。只有真实接入证明现有边界无法干净承载时，才记录具体需求和限制，评估是否修订本合同，并以最小必要改动演进模型。
