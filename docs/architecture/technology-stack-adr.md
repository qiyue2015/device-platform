# ADR-0001 后端基础技术栈与消息基础设施

## 决策

Device Platform 后端采用以下长期基础技术栈：

- Go，使用标准 `net/http` 与 Chi v5 组织 HTTP 路由和中间件；
- OpenAPI 3.x 与 `oapi-codegen` 维护和生成 HTTP 契约边界；
- PostgreSQL、`pgx/v5`、`sqlc` 与 Goose 承载权威业务状态、类型安全 SQL 和 schema migration；
- NATS JetStream 承载内部可靠异步消息传输、任务唤醒、消费者解耦和削峰；
- Redis 承载可重建的实时状态、TTL、缓存、限流和短期协调；
- `slog`、OpenTelemetry 与 Prometheus 承载日志、链路和指标；
- 后端保持模块化单体，API、Outbox Publisher 和各类 Worker 可以独立进程部署，但共享领域合同和数据库事实。

这是一项已接受的架构决策，不因后续会话、个人框架偏好或单个组件流行度重新选择。若没有本文“重新开启条件”所列的新证据，实现与评审应以本决策为默认前提。

本文只定义后端重建的目标架构，不记录旧实现状态。

## 决策背景

平台边界已经包含 Project/Device 管理、第三方 Provider、异步命令下发与结果确认、Provider callback、Webhook、Audit、幂等、重试和崩溃恢复。它们不是普通 CRUD 的可选增强，而是长期运行模型的基础能力。

设备规模、心跳频率和峰值尚未形成受验收的固定数字，因此不能把某次讨论中的 `1000` 台设备当作容量上限。基础设施需要在不虚构吞吐数字的前提下支持水平扩展、故障隔离和积压恢复，避免在产品规模增长后重写命令、回调与投递模型。

## 为什么选择显式 Go 组件栈

Chi 保持在标准 `net/http` 生态内，领域层不需要依赖框架 Context、ORM 类型或代码生成约定。OpenAPI、PostgreSQL、认证、消息和可观测性分别使用职责明确的成熟组件，可以独立升级和测试。

GoFrame 2 提供更接近 Laravel 的一体化开发体验，但当前产品最困难的部分是设备命令事实、异步恢复和 Provider 证据语义，而不是表单 CRUD。GoFrame 的迁移、认证和持久任务能力仍不能替代专门组件，同时会通过 HTTP、ORM、通用值类型和 CLI 约定扩大框架锁定。因此 GoFrame 保留为有明确团队经验时的备选，不作为默认技术底座。

Gin 与 Echo 都可以提供 HTTP 路由，但在 OpenAPI-first 和标准库优先的前提下，没有足够收益替换 Chi。Kratos 和 go-zero 更偏 protobuf、服务治理和微服务工程，当前模块化单体采用它们会提前引入不需要的服务边界和生成约束。

## 为什么从第一版采用 NATS JetStream

当前平台存在不同可靠性和吞吐特征的异步工作：

- Command 投递低频但不能丢失、不能因重复消费产生重复物理动作；
- Provider callback 可以重复到达，但必须持久化、验签、去重和恢复；
- Webhook 需要独立重试、死信、受控重放并隔离外部端点故障；
- 设备连接观察或心跳若由真实 Provider 合同启用，可能高频、可合并，并且不能挤占命令资源。

只使用 PostgreSQL 扫描任务表可以满足早期正确性，但会把任务唤醒、消费并发、事件订阅和业务事实访问全部耦合到数据库。既然异步边界属于已知基础建设，本项目不把“数据库队列以后再换消息系统”作为最终形态。

JetStream 的选择理由是：

- Go 客户端与 Go 服务模型匹配；
- 支持持久 Stream、durable consumer、显式 Ack、重新投递和工作队列保留策略；
- Subject 能隔离 Command、Callback、Webhook 与未来连接观察流量；
- 同一消息可以按合同支持工作队列或多个独立消费者；
- API 与 Worker 可以独立扩容，未来拆分模块时不需要重新定义内部通信语义；
- 相比 Kafka，部署和日常运维更轻，符合当前以可靠业务处理而非长期海量分析流为主的产品形态。

JetStream 不提供业务层“恰好一次”。平台统一采用至少一次投递，依靠 PostgreSQL Transactional Outbox、Consumer Inbox/去重和领域条件更新保证最终效果幂等。NATS 的消息去重窗口只能优化重复发布，不能成为正确性依据。

## PostgreSQL、NATS 与 Redis 的固定职责

| 组件           | 权威职责                                                                                                          | 明确不负责                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| PostgreSQL     | Project、Device、Command、Attempt、Result、RawMessage、Event、Outbox、Webhook Delivery、Audit、消费去重与恢复进度 | 不承担高频通知广播，不用轮询替代全部消息传输      |
| NATS JetStream | 已持久事实的异步传播、任务唤醒、消费者解耦、积压和重新投递                                                        | 不成为 Command、设备状态或 Audit 的唯一事实来源   |
| Redis          | 在线 TTL、可重建实时状态、缓存、限流、短期协调                                                                    | 不保存不可恢复的命令、结果、Outbox 或审计唯一副本 |

Broker 不可用时，已经提交到 PostgreSQL 的业务事实和 Outbox 仍然存在；恢复后继续发布。Redis 不可用时，命令和审计事实仍可恢复，高频可合并状态按可靠性规范降级；但 Redis 不可用不能绕过 Device Type profile，`online_only` 创建与派发在无法取得可信新鲜 `online` 证据时必须失败关闭。

## 未选择方案

### PostgreSQL 数据库队列作为最终形态

保留 PostgreSQL 作为唯一业务事实和 Broker 故障恢复来源，但不把定时扫描数据库作为长期唯一异步传输。

### Redis Streams

Redis 已承担缓存、TTL 和限流。再让它承担核心可靠消息总线会混合不同持久性责任，并扩大 Redis 故障影响面，因此不采用。

### RabbitMQ

RabbitMQ 的可靠队列、路由和运维生态成熟，能够满足需求。如果组织已经具备统一 RabbitMQ 平台和成熟运维能力，可以触发 ADR 复审；在没有该前提时，JetStream 与 Go、Subject 事件模型及未来模块拆分更匹配。

### Kafka

Kafka 适合超大规模顺序事件流、长期回放和数据分析平台，但当前核心是可靠业务任务而不是保存全部遥测历史。第一阶段使用 Kafka 会引入更重的集群、分区、容量与运维要求。未来若长期遥测和多下游分析正式进入产品边界，可以将规范化事件导入 Kafka，不需要让 Kafka 取代全部业务消息。

### 直接依赖 Broker，不使用 Outbox

拒绝 `database commit -> best-effort publish` 和 `publish -> database commit` 两种双写。任何一边失败都可能造成已受理命令没有消息，或消息已消费但业务事实不存在。必须使用 Transactional Outbox。

## 约束与代价

- 生产环境增加 NATS JetStream 的部署、升级、容量、备份和告警责任；
- 所有发布者和消费者必须实现版本化消息、幂等、链路关联和可观测性；
- 模块化单体不能因为使用消息总线而把本可在同一事务完成的状态写入拆成不必要的最终一致性；
- 不允许用 NATS 替代已经冻结的领域状态机、事务边界和证据语义；
- 只有目标部署通过消息、恢复和故障测试，才能声明该架构已实现并可上线。

## 重新开启条件

只有出现以下任一可验证变化时，才重新评估本 ADR：

1. 组织强制使用已有统一消息平台，并提供可验证的可用性、运维和成本优势；
2. 长期遥测、全量事件回放或分析订阅正式进入产品合同，且 JetStream 经压测不能满足保留或吞吐要求；
3. JetStream 在目标部署环境无法达到已冻结的 RPO、RTO、安全或合规要求；
4. 官方维护状态、协议兼容或关键客户端风险发生实质变化；
5. 真实容量与故障演练证明当前方案存在无法通过扩容或配置解决的结构性瓶颈。

重新开启必须提交新 ADR，包含当前数据、替代方案、迁移影响和回滚方案。新 ADR 被接受前，本文继续有效。
